# Set up your private profile

Start from `examples/profile.json`, copied to `local/profile.json`. The example is entirely fictional. Replace its names, contact details, employers, education, metrics and search preferences before using it with your own job search. Keep private documents, profiles and browser state out of the public source tree.

| Field | Purpose |
| --- | --- |
| `applicant.identity` | Form answers: full name, first name, last name, email and phone. Supply name parts explicitly; JobLazy does not infer how a full name should be split. |
| `applicant.address` and `applicant.links` | Known location and professional links for application forms. |
| `resume.candidate` | Contact information printed on the CV. Keep it consistent with `applicant.identity`; both sections currently require editing. |
| `resume.summary`, `resume.experience`, `resume.education`, `resume.projects` | Canonical career evidence. Include only factual statements and exact dates/metrics you can support. Preserve distinctions between proposals, prototypes and shipped work. |
| `resume.experience[i].employer_context` | Optional sourced description of that employer's products and sector. Store the source URL, short supporting quote, publication/review dates, scope, and whether a classification is an inference. Company context does not establish personal skills or responsibilities. |
| `targeting` | Your role tracks, locations, preferred company types and explicit exclusions. Replace the example preferences. |
| `targeting.career_preferences` | Optional text stating your actual career interests and priorities. Application-answer drafting and review can use it to explain role fit. It does not establish skills, employer familiarity, personal history or consent, and is kept out of CV experience sources. |
| `targeting.config.location.city` and `.country` | Explicit preferred work location, separate from residential address. Recognized plain-text preferred-location questions can reuse both values; neither is inferred from residence or phone. |
| `targeting.config.location.authorized_in` | Optional list of countries where you currently have work authorization, supplied as a factual statement. This is separate from residence, preferred locations and future sponsorship needs. |
| `search_location` | A queue-priority hint; full job descriptions and targeting rules still determine ranking. |
| `discovery_preferences.title_filter.deprioritized` | Optional title phrases for lower-interest fallback work. Each matching role receives one scheduling penalty, regardless of overlapping aliases. Roles remain eligible for full assessment; this is not a rejection filter. |
| `minimum_score` | Minimum assessed fit score for CV generation. A score does not establish eligibility or hiring odds. |
| `writing_preferences` | Optional string describing tone, emphasis and factual limitations for tailored material. |
| `employment_title_options` | Optional user-confirmed alternatives for a specific employment record; never infer them from a target posting. |
| `facts` | Optional extra canonical evidence, as objects with a `text` field. Leave empty if the résumé contains the relevant evidence. |
| `answers` | Application-specific answers created through the `answer` command. Keep the exact observed question and application scope. |
| `application_defaults` | Optional explicitly confirmed reusable application preferences. Exact scoped answers take precedence. See the supported fields below. |

Leave unknown facts blank. Do not copy generated CV language or previous generated application answers back into canonical evidence unless you have independently established those facts. JobLazy assigns source IDs from the saved résumé and additional facts; you do not need to write source IDs yourself.

For a genuinely available alternative title, a fictional record might be:

```json
{"experience_index":0,"company":"Fictional Software Ltd","dates":"2023–2025","original_role":"Operations Associate","allowed_roles":["Client Service Manager"],"source":{"method":"operator_confirmed","verbatim":"Both titles were available for this role."}}
```

Place records in the `employment_title_options` list. The original title always remains an allowed choice. Employer, dates and original title must match the indexed résumé entry exactly. Tailoring selects only from that employer's confirmed choices and records the reason and source pointer. This does not authorize new responsibilities or management claims. Use `writing_preferences` to request selective use where relevant to the posting.

Reusable defaults require `source.method: operator_supplied` and should retain the user's statement and confirmation date. Supported values are `salary.annual_amount` (positive integer) with `salary.currency: GBP`, `availability.month` (`YYYY-MM`) with optional `availability.exact_day` (a full `YYYY-MM-DD` date), and `sponsorship.required` (boolean) with `sponsorship.countries` (explicit country list). Recognized salary-expectation questions require a structured, unambiguous UK posting; the mapper does not infer its country from the candidate's residence or convert currencies. It never turns expected pay into current earnings. Month-only availability fills recognized free-text start questions without inventing a day or contractual notice period. A confirmed full date fills recognized start-date questions as a date or a readable sentence. It must be valid, not past, and consistent with the supplied month. Native and supported Ashby date controls reject month-only, ambiguous numeric and impossible dates, including invalid scoped answers. Interval dropdowns remain unresolved without an explicit interval answer. Sponsorship defaults fill recognized simple Yes/No questions only when the question or structured posting identifies a covered country. Compound options and additional instructions still require scoped answers. Defaults do not accept consent or establish citizenship. Invalid or duplicate scoped answers cannot silently fall back to a default. These values are still part of material/profile bindings, so changing them does not silently reapprove an existing checkpoint.

Run `.\.venv\Scripts\python.exe -m joblazy doctor --profile local/profile.json` after editing. It checks the expected JSON structure and agreement between form and CV names, emails and phone numbers. Conflicting values stop processing before model or browser actions. Formatting differences in phone numbers are allowed; missing name parts, email or phone produce warnings without inventing values. The current CV pipeline requires at least one experience entry with source bullets. A passing check establishes structure and contact consistency, not factual accuracy or application eligibility.

`example_only` starts as `true`, which prevents live employer preparation. Set it to `false` only after replacing the fictional profile with your own verified data. This flag does not validate your edits. Start with one ranked role and review the generated CV before using `assist` to prepare a real application.

The sample board list contains one Ashby board for a scanner check. Replace it with your intended search sources. Existing Career Ops users can use `import-profile` to migrate their canonical files and configured boards, but new users do not need that project.

Ranking can cite supplied employer context through the existing `employment.i` reference. This is useful when the bounded evaluator cannot establish an employer's sector from its name alone. Use a reliable source and keep the employer description separate from candidate duties: working at a consumer technology company does not establish B2B SaaS renewals, software engineering or product-strategy ownership. Preserve uncertainty when the company or classification is ambiguous. This context is not added to the CV claim-source bank. Adding it changes profile/material bindings but does not rewrite or reapprove existing documents. No automatic company research is currently performed.

When a form needs an answer, inspect it with `show JOB_ID`. Supply an observed answer with `answer`, or complete it manually in the assisted browser. Salary, availability, authorization, demographic choices and consent are not invented. After a manual browser handoff, record its outcome before retrying that application.

Required narrative answers receive a separate factual review. If that review identifies missing candidate information, drafting pauses immediately and records the requested facts instead of attempting another rewrite. Correctable wording still receives a bounded repair attempt. A model's missing-fact report is a review judgment, not proof that experience is absent; check it against the canonical sources before supplying or changing facts.

New material checkpoints preserve a reviewed CV when only form name parts, consistent form contact values, or the form-only GitHub/portfolio/website links change. Printed CV contacts, career evidence, residence, targeting, writing preferences and unknown fields remain bound to the saved materials; changing them invalidates reuse. Conflicting form/CV contact values also stop reuse. Older version 1 checkpoints retain their stricter full-profile binding and are not silently upgraded. Application-scoped answers remain separate from CV inputs.

The mapper can reuse an explicit `authorized_in` fact for recognized positive current-work-authorization Yes/No questions. When the question names a country, such as “Do you have the legal right to work in the UK?”, that question supplies the country and the mapping records its label as evidence. When it refers to an unnamed job country, the posting must provide one fully represented structured country with no unexplained or conflicting location text. Current country aliases cover the UK, US and Canada. An absent authorization entry, unsupported wording or an unresolved unnamed country leaves the question unanswered. It never derives a negative answer from a missing entry, or infers citizenship, relocation, future sponsorship or consent. Exact application-scoped answers take precedence. Reused authorization records the candidate fact pointer and the question or posting evidence without creating an operator-supplied answer. Answering a country-specific factual question does not establish overall eligibility for the role.
